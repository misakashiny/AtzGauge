## 二、★ 根因：转速页是全工程**唯一**没做插值的表

主表固件的数据来自 BLE ELM327，**约 10Hz**（不是 CAN 100Hz）。
`main/export_path/ui.c` 的 `my_timerMain()` 里，每个表盘的写法：

| 表盘 | 写法 | 是否插值 |
|---|---|---|
| 车速页 | `anim_step_i32(s_disp_spd, ucSpeed, ANIM_THRESH_SPD)` | ✅ 有 |
| 温度/信息/油压页 | `disp_item_update(&s_disp_x, ..., ANIM_THRESH_TEMP)` | ✅ 有 |
| 指针页 | `disp_item_update(&s_disp_needle, ..., needle_thresh)` | ✅ 有 |
| **转速页** | `usRpm` 直连，且只在整数变化时写控件 | ❌ **无** |

转速页原文（修复前）：

```c
/*RPM page: direct output, no animation delay (CAN 100Hz data is already clean)*/
if (scr == ui_ScreenPageRpm) {
    static int32_t s_last_rpm = -1;
    if ((int32_t)usRpm != s_last_rpm) {
        s_last_rpm = (int32_t)usRpm;
        lv_label_set_text_fmt(ui_RpmPageArcLabelRpmText, "%d", (int)usRpm);
        lv_arc_set_value(ui_RpmPageArcRpmBack, (uint32_t)usRpm*100/SWEEP_RPM_PEAK);
    }
}
```

**关键证据**：同文件第 208 行定义了 `#define ANIM_THRESH_RPM 50`，第 213 行的注释明写
"**The RPM/Speed pages** must update label + arc together, which differs from disp_item_update,
so a local copy is kept" —— 但 `ANIM_THRESH_RPM` 从来没有被任何地方使用。
**这说明转速页漏掉插值不是设计选择，而是上游的遗漏。**

后果：转速弧以约 **10 次/秒** 跳变（每次 OBD 采样跳一格），而车速弧是 ~62 次/秒连续逼近。
转速又是最常看的表，所以"整体观感帧率低"。

> 另外该行注释的前提"CAN 100Hz 数据已很干净"只在 **ATMA/CAN 广播**路径成立；
> 走 BLE ELM327 时数据率低一个数量级，前提不成立。

## 三、修复内容（3 个文件，均为最小改动）

### 3.1 `main/export_path/ui.c` —— 转速页改用与车速页相同的插值

```c
if (scr == ui_ScreenPageRpm) {
    static int32_t s_disp_rpm = 0;
    static int32_t s_last_rpm = -1;
    if (IN_SWEEP) { s_disp_rpm = (int32_t)usRpm; }      // 扫表本身已是平滑斜坡，不叠加
    else { s_disp_rpm = anim_step_i32(s_disp_rpm, (int32_t)usRpm, ANIM_THRESH_RPM); }
    if (s_disp_rpm != s_last_rpm) {
        s_last_rpm = s_disp_rpm;
        lv_label_set_text_fmt(ui_RpmPageArcLabelRpmText, "%d", (int)s_disp_rpm);
        lv_arc_set_value(ui_RpmPageArcRpmBack, (uint32_t)s_disp_rpm*100/SWEEP_RPM_PEAK);
    }
}
```

★ `usRpm` **本身不动**：后面的主题表页、指针页、温度页、行程统计都必须继续拿原始值。
只有屏幕上的弧与数字用平滑值。

### 3.2 `main/theme_engine/theme_loader.c` —— 主题表盘也补上插值

自定义主题（带 `layout.json` 的主题）的弧/条原来是**直连原始值**：

```c
case BINDING_KIND_ARC:  lv_arc_set_value(bind->widget, clamped);                 // 跳变
case BINDING_KIND_BAR:  lv_bar_set_value(bind->widget, clamped, LV_ANIM_OFF);    // 跳变
```

现在合并为一个分支，加 `theme_anim_step()`（按绑定自身的量程缩放步长：
超过量程 1% 的差值每拍吃掉一半，小差值每拍走 1 个单位），并给 `theme_binding_t`
增加 `shown` / `shown_init` 两个字段。

> 当前设备的内置三套主题（`themes/builtin/{default,amber,ocean}`）都是**纯配色、无 layout**，
> 所以这一条对本机暂时不生效；它是给"以后装自定义主题"准备的（项目里已有
> `theme_store/boost_oil_example/theme.bin` 这套 4MB 主题）。

### 3.3 `main/app_main.c` —— 临时帧率探针

主表固件没有 `/perf`，无法量化。加了一个**只读计数器**：统计"每秒真正写进控件的表盘次数"
（`ui_updates/s`），每 2 秒打一行：

```
I (7439) AtzPerf: ui_updates/s=0.0 total=0 free_sram=10275
```

它直接就是"顺滑度"本身：无数据时 0；有数据时，修复前转速页约 10/s，修复后应约 60/s。

> ⚠️ 为什么不用 LVGL 渲染事件：**LVGL 8.4 没有 `LV_EVENT_RENDER_START` / `LV_EVENT_RENDER_READY`
> 与 `lv_disp_add_event_cb`** —— 那是 LVGL 9 的 API（从表 xiaozhi 的 `/perf` 用的是 LVGL 9）。
> 第一版照抄导致编译报 `undeclared`，已改成本计数器。

## 七、怎么验证"确实变顺了"

`ui_updates/s` 就是答案。**需要真实的 OBD 数据**（BLE ELM327 约 10Hz）：

1. 把 Vgate 插到车上（或给它供 12V），设备进 **BLE SCAN** 页选它连接；
2. 翻到 **RPM 页**；
3. 看串口日志里的 `AtzPerf:` 行：
   - 修复前：约 **10/s**（跟着 OBD 采样跳）
   - 修复后：应约 **60/s**（16ms 页面刷新节拍，连续逼近）

> 当前设备没接 Vgate，所以 `ui_updates/s=0`（没有数据 → 表盘不动），这是预期。

## 七之二、★ 台架实测：临时合成转速斜坡（已完成，结论决定性）

为了**不上车也能量出数字**，加了一段临时的合成转速斜坡并烧录验证。全部代码用
`ATZ_SYNTH_RPM` 宏包裹，共 4 处注入点，发布前可一键回退。

### 7.2.1 开关位置

`#define ATZ_SYNTH_RPM 1` 定义在 **`main/export_path/ui_ext.h`** —— 因为 `ui.c` 和 `ui_ext.c`
是两个编译单元，宏必须放共享头才两边都看得到。

### 7.2.2 注入点（`grep -rn "ATZ_SYNTH_RPM" main/` 可全部定位）

| 文件 | 位置 | 作用 |
|---|---|---|
| `export_path/ui.c` | 文件上部 `atz_synth_rpm_inject()` | 造 0..4000rpm 三角波（周期 4s），**按 10Hz 采样** |
| `export_path/ui.c` | `my_timerMain()` 内、`obd_data_get_snapshot()` 之前 | 调用注入 |
| `export_path/ui.c` | `ui_init()` 末尾 | 预创建 RPM 页 |
| `export_path/ui_ext.c` | `boot_enter_default_page()` 内 | 把启动页强制改成 RPM 页 |

### 7.2.3 两个关键设计点（都是踩过才明白的）

1. **必须注入在"快照源"，不能注入 `usRpm`。**
   每个非扫表 tick 都会用 `obd_data_get_snapshot()` 的结果覆盖 `usRpm`，
   直接写 `usRpm` 会被立刻冲掉。
2. **RPM 走固件自带的 override 钩子，speed 不用。**
   - RPM：`obd_data_rpm_override_set(true, rpm)` —— `obd_data_get_snapshot()` 在 override
     使能时返回 override 值。**不能用 `obd_data_set_rpm()`**，它只写内部 `s_rpm_smooth`，
     接上 Vgate 后会被 BLE 采样覆盖。
   - Speed：`obd_data_set_speed(rpm/50)` —— 无适配器时没有任何别的东西调用它，无需钩子。
3. **启动页覆盖必须放在启动流程里。** 在 `ui_init()` 里 `lv_scr_load()` 会被随后的
   启动序列（`boot_enter_default_page()`）覆盖掉，所以要在后者内部改
   `target_scr` / `target_init`。

### 7.2.4 实测数字（决定性证据）

用新写的 `tools/capture-boot.py` 硬复位并**从第一行**抓日志：

```
I (3439) AtzPerf: ui_updates/s=0.0 total=0 free_sram=17487   ← 启动早期，RPM 页还没挂上
I (7439) AtzPerf: ui_updates/s=9.5 total=19  free_sram=5307  ← ≈10/s = 合成数据源速率本身
I (9439) AtzPerf: ui_updates/s=49.0 total=117 free_sram=5099 ← 稳定进入 46~50/s
I (33439) AtzPerf: ui_updates/s=49.5 total=1270 free_sram=9555
```

**结论：修复前 ~10/s → 修复后 ~48/s（约 5 倍）。**

- 上限约 48 而非 60：`anim_step_i32` 在差值 ≤ 阈值时每次只走 ±1，4000rpm 量程下要若干
  tick 才收敛；且 UI timer 节拍与 LVGL 实际渲染刷新存在耦合。但已远超 10/s，肉眼可见连续。
- `free_sram` 稳定在 5~14KB，**0 新增错误 / 无 abort / 无看门狗**。

> ⚠️ **但这个指标不等于"丝滑"，见第九节。`ui_updates/s` 只是数据写入次数，
> 真正决定肉眼观感的是 `frames/s`，而后者只有 13.6。**

## 九、★ 真实帧率定位：「不够丝滑」的根因（2026-09-28 第二轮）

用户反馈「还是不够丝滑 / 像帧率卡卡的」。重新做探针后**推翻了上一轮的自我判断**。

### 9.1 关键纠正：`ui_updates/s` 不是帧率

上一轮把 `ui_updates/s≈48` 当作流畅度指标，**这是错的**。两者差了 3.5 倍：

```
I (9439)  AtzPerf: ui=48.5/s flush=163.0/s px/s=1749358 frames/s=13.5 (ceil=125.0/s @16ms) free_sram=5027
I (29439) AtzPerf: ui=48.0/s flush=162.0/s px/s=1757100 frames/s=13.6 (ceil=125.0/s @16ms) free_sram=9547
```

| 指标 | 含义 | 实测 |
|---|---|---|
| `ui/s` | 每秒写进控件的次数（插值路径在工作） | 48 |
| `flush/s` | 每秒 flush 回调次数（= band 数） | 163 |
| `frames/s` | **每秒真正推上屏的整屏等价帧数** | **13.6** |
| `ceil/s` | LVGL 刷新定时器允许的上限（16ms 周期） | 125 |

**`frames/s` 才是眼睛看到的，只有 13.6，用掉了上限的 11%。**

### 9.2 根因：面板 SPI 传输受限（不是渲染受限）

- 屏为 QSPI 四位模式 @80 MHz，理论 **40 MB/s**；实测仅 **3.51 MB/s（8.8%）**
- 驱动每渲染一个 band 发 **3 个 SPI 事务**（CASET+RASET+RAMWR），40 行 = 9 band
  = **27 事务/帧**；反推每事务固定开销约 **1.8 ms**（远超 CS 建立时间）
- 交叉验证：`1.77e6 px/s ÷ 129600 px/帧 = 13.66 帧/s`，与实测 13.6 **完全吻合**
  → 确认是传输瓶颈，CPU 渲染不是问题

### 9.3 试过并已回退的两个方案（别再重复）

1. **PSRAM 全屏双缓冲（506 KB）** —— 分配成功，运行时必失败：
   ```
   E spi_master: setup_dma_priv_buffer: Failed to allocate priv TX buffer
   E lcd_panel.io.spi: spi transmit (queue) color failed
   ```
   → `ui=0.0/s frames/s=0.0`，**UI 完全冻结**。
   原因：`esp_lcd` 的 SPI IO 层**从不设置 `SPI_TRANS_DMA_USE_PSRAM`**，
   于是 `spi_master` 对每个 PSRAM chunk 额外申请内部暂存：
   `need_malloc = is_ptr_ext && !(flags & SPI_TRANS_DMA_USE_PSRAM)`；
   `trans_queue_depth=10` × 28 KB ≈ 282 KB，而运行期内部 SRAM 只剩 5~17 KB。
   证据：`backup/boot-log-20260928-psram-fail.txt`

2. **抬高 band 到 90/60 行（配合 queue_depth 降到 2）** ——
   90 行（126 KB）malloc 直接失败；60 行（84 KB）malloc 成功但**饿死后续 init 分配
   → `abort()` → 反复重启**（26 秒重启 7 次）。**40 行是安全上限。**

`max_transfer_sz` 和 `trans_queue_depth` 均已还原为原值，`ST77916.h` 只留说明性注释。

### 9.4 已确认正确的配置（不是问题所在）

- SPI 时钟：先 3 MHz 读寄存器 0x04，再被 `ESP_PANEL_LCD_SPI_CLK_HZ` 覆盖为 **80 MHz**
  （`ST77916.c:712`）。第一个 `io_handle` 泄漏但无害
- QSPI：`quad_mode=1` / `use_qspi_interface=1` 生效，数据阶段带 `SPI_TRANS_MODE_QIO`
- LVGL 缓冲：40 行 ×2 内部 DMA（56 KB），`full_refresh=0`

### 9.5 要真正解决必须动 IDF（超出本项目范围）

1. 给 `esp_lcd_panel_io_spi.c` 的 `tx_color` 数据阶段加 `SPI_TRANS_DMA_USE_PSRAM`
   → PSRAM 全屏缓冲免掉内部暂存 → **27 事务/帧降到 3 事务/帧**，理论 4~10 倍提升
2. 或 fork `esp_lcd_st77916`，把 CASET/RASET/RAMWR 合并为一个长事务

两条路都要求维护 IDF/驱动补丁，与项目"只改板型目录"的铁律冲突，故暂不实施。
