# 小智AI 读取车况数据 —— 多 ESP32 架构方案

> 目标：小智AI 实时获取仪表（OBD）数据，据此做出语音提示
> 基础：obd_brz_gauge 已内置 ESP-NOW 主从架构
> 日期：本会话

---

## 零、名词解释（新手先看这段）

### ESP-NOW 是什么

乐鑫（ESP32 厂家）自研的**无线通信协议**，跑在 2.4G WiFi 射频上，但**不是 WiFi**：

| 特点 | 说明 |
|---|---|
| 不用路由器 | 两块板直接通信，不需要连网 |
| 不用建连接 | 广播式发送，没有 WiFi 握手/认证开销 |
| 延迟极低 | 毫秒级 |
| 数据包小 | 一包最多 250 字节 |
| 距离 | 视距 100~200 米 |

**一句话：ESP-NOW = 两块 ESP32 之间的"对讲机"**，适合传小块数据。

### MASTER / SLAVE 是什么

**主从角色分工**，用比喻最直观：

- **MASTER（主表）= 广播电台** 📻 —— 有数据源，负责往外发
- **SLAVE（从表）= 收音机** —— 不产生数据，只负责收

一个主表可对应**多个从表**（一个电台无数收音机听）。

### 为什么必须这么设计

因为 **Vgate 蓝牙适配器只允许一个客户端连接** —— 车上的数据只有一块板能读到。
这块板当 MASTER 广播出去，其余板当 SLAVE 接收，于是不用各自连车也能拿到实时数据。

### 本项目里的对应关系

```
[车] → Vgate (蓝牙)
         ↓
  ESP32-A 微雪板 ── MASTER ── 读OBD + 显示仪表 + 广播车况
         ↓ ESP-NOW
  ESP32-B 小智AI ── SLAVE ─── 只管听 → 收到车况 → 判断 → 语音提示
```

主表每秒广播约 10~20 次，每次一小包：

```
{RPM: 2400, 车速: 65, 水温: 92, 电压: 14.1, ...}
```

从表收到就更新本地缓存（`espnow_link_start_slave()` 自动完成），AI 逻辑再从缓存读取。

### ⚠️ 容易混淆的点

这里的 **SLAVE 与"蓝牙主从""SPI 主从"无关**，纯粹是角色命名。
从表**功能不受限**，照样能跑完整的 AI 对话。

## 一、先纠正一个前提：不能"多块同时读取"

**ELM327 蓝牙适配器只允许一个客户端连接。** obd_brz_gauge 的 README 明确写了这点：

> 一个 ELM327 蓝牙适配器只允许一个客户端连接，多块表无法各自直连。

而且让多块板各自插适配器轮询，会**成倍加重 OBD 总线负载**，得不偿失。

✅ **正确做法：一块读，其余接收。**

## 二、好消息：原项目已经内置主从架构

`main/bsp_obd_dsp/espnow_link.h` 定义了三种角色：

| 角色 | 行为 |
|---|---|
| `ESPNOW_ROLE_MASTER` | 读 ELM327 + 通过 ESP-NOW 广播给从表（WiFi 开） |
| `ESPNOW_ROLE_SLAVE` | **只接收主表数据，写进本地 OBD 数据缓存**（不连 ELM327） |
| `ESPNOW_ROLE_STANDALONE` | 单机模式，功能完整但不联网 |

关键 API：

```c
void espnow_link_start_master(void);   // 主表
void espnow_link_start_slave(void);    // 从表：收数据 → 写入本地 OBD 数据缓存
void espnow_link_bind_master(const uint8_t mac[6]);  // 通过 BLE 配对拿到主表 MAC 后绑定
bool espnow_link_slave_has_data(void);               // ~2s 内是否收到主表数据
const char *espnow_link_get_master_name(void);
void espnow_link_broadcast_threshold(uint16_t thresh);  // 阈值同步
```

> ★ **`espnow_link_start_slave()` 会把收到的数据写进本地 OBD 数据缓存** —— 这就是小智AI 板的接入点：
> 先让 ESP-NOW 把数据灌进缓存，AI 逻辑再从缓存里读。

## 三、目标架构

```
        [车 OBD 口]
             │ 有线插入
     [Vgate iCar Pro 2S]
             │ BLE（唯一客户端）
             ▼
  ┌──────────────────────────────┐
  │ ESP32-A（微雪 1.85 板）       │
  │  角色：MASTER                 │
  │  · 读 OBD                     │
  │  · 显示仪表（LVGL）           │
  │  · ESP-NOW 广播车况           │
  └──────────────────────────────┘
             │ ESP-NOW（2.4G）
             ▼
  ┌──────────────────────────────┐
  │ ESP32-B（小智AI 板）          │
  │  角色：SLAVE                  │
  │  · 收车况 → 写入本地缓存      │
  │  · 阈值判断                   │
  │  · 语音播报 + 云端对话        │
  └──────────────────────────────┘
```

## 四、这个架构最大的好处：绕开了射频共存

| | 单板合并（不推荐） | 双板 + ESP-NOW（本方案） |
|---|---|---|
| 射频使用 | **一块板同时** BLE(OBD) + WiFi(云端音频) | A 板只用 BLE，B 板只用 WiFi |
| 冲突 | 严重，语音卡顿 + OBD 丢包 | 基本无冲突 |
| 原因 | 两种射频协议争抢连续时序 | ESP-NOW 本身就是 WiFi 家族，与 WiFi STA 同信道共存，且每秒才几包小数据，负担极轻 |

**所以双板方案的稳定性远高于单板合并。** 这也是原项目采用主从架构的原因。

## 五、小智AI 板要做的改造

| 模块 | 来源 | 工作量 |
|---|---|---|
| `obd_data_cache`（数据结构+缓存） | 从 obd_brz_gauge 移植 | 小，可直接复用 |
| `espnow_link`（只取 slave 部分） | 从 obd_brz_gauge 移植 | 中，ESP-NOW 收包 + 绑定逻辑 |
| 阈值规则引擎 | 新写 | 小，约 100~200 行 |
| 语音触发 | 对接小智AI 音频层 | 中 |
| （可选）MCP 工具 | 新写 | 中，让 LLM 能查询车况 |

**难度评估**：比"两个完整固件合并"**简单得多**。因为不需要 LVGL/显示逻辑，也不需要 ELM327 BLE 客户端，只加"收数据 + 判断 + 播报"三件事。

## 六、播报方式怎么选（重要）

| 方式 | 延迟 | 需联网 | 适合 | 实现难度 |
|---|---|---|---|---|
| **本地预录音频** | <100ms | ❌ | **安全告警** | 最简单、最可靠 |
| LLM 生成播报 | 1~3s | ✅ | 闲聊式描述 | 需服务端支持 |
| MCP 查询 | 1~3s | ✅ | 用户主动问答 | 官方支持 |

> ★ **强烈建议：安全告警用本地预录音频，问答用 MCP。**
> 水温过高的警告不可能等 2 秒云端往返；而且本地音频断网也能用。

## 七、告警规则示例（阿特兹）

| 条件 | 播报内容 | 优先级 |
|---|---|---|
| 水温 > 105°C | "水温偏高，请注意" | 中 |
| 水温 > 115°C | "水温过高，请立即靠边停车" | **高** |
| 转速 > 6200 rpm | "转速接近红线" | 低 |
| 车速 > 120 km/h | "已超速" | 低 |
| 行驶中电压 < 12.0V | "电瓶电压偏低" | 中 |
| 进气温度 > 60°C | "进气温度偏高" | 低 |
| 发动机负荷持续 > 90% | "发动机持续高负荷" | 低 |

⚠️ **告警必须节流**（同一条例如 30 秒内只播一次），否则会疯狂刷语音。
原项目就是这么做的：刹车温度/油压报警限制为 30 秒一次。

## 八、用户主动问答（MCP 方式）

把车况注册成 MCP 工具后，用户可以直接问：
- "小智，现在水温多少？"
- "我的转速是多少？"
- "车子有没有异常？"

这是 xiaozhi-esp32 作为 **MCP 架构**的天然用法（项目定位就是 MCP-based chatbot）。

## 九、实施阶段（建议按顺序）

| 阶段 | 内容 | 验证点 |
|---|---|---|
| 1 | 两块板各自跑通（仪表 MASTER / 小智AI 原版） | 各自功能正常 |
| 2 | 小智AI 板加 ESP-NOW SLAVE，**先只串口打印收到的数据** | 串口能看到实时车况 |

**阶段 2 是关键里程碑** —— 先证明"数据通路"通了，再谈播报逻辑。

## 十、技术坑（重点）

1. **ESP-NOW 信道必须和路由器一致**
   小智AI 板要连路由器上云，WiFi STA 会锁定路由器信道；ESP-NOW 必须用同一信道，否则收不到包。
   原项目在主表侧处理了这个，移植时要确认。

2. **配对走 BLE**
   从表要先通过 BLE 配对拿到主表 MAC，再绑定 ESP-NOW（`espnow_link_bind_master`）。所以小智AI 板也会短暂占用 BLE。

3. **主表的射频负担**
   MASTER 同时跑 BLE(OBD) + WiFi(ESP-NOW)，原项目在 sdkconfig 里开了软件共存。
   可行，因为 ESP-NOW 流量很轻（每秒几包），远轻于音频流。

4. **硬件门槛**
   小智AI 板要求 **Flash ≥ 8MB、PSRAM ≥ 2MB**（官方要求）。推荐 ESP32-S3 N16R8。

5. **音频仲裁**
   告警播报和用户对话**不能同时出声**，需要做互斥仲裁。

## 十一、结论

| 问题 | 答案 |
|---|---|
| 能实现吗？ | ✅ 能，且原项目已有现成的主从基础设施 |
| 要多块 ESP32 同时读吗？ | ❌ 不需要，**一块读、一块收**，反而更稳 |
| 比单板合并难吗？ | ✅ **简单得多**，且稳定性更好 |
| 主要工作 | 移植 ESP-NOW slave + 写阈值规则 + 接音频 |
| 推荐播报方式 | 安全告警=本地预录音频；问答=MCP |
