# 小智AI 接入仪表主从架构 —— 技术分析与关键障碍

> 依据：`obd_brz_gauge/main/bsp_obd_dsp/espnow_link.c` 源码 + 小智AI 官方文档
> 日期：本会话

---

## 一、先纠正一个概念：小智AI 没有"主从模式"

**`xiaozhi-esp32` 是纯语音助手固件，它没有主/从/单机的概念。**

主从是 **obd_brz_gauge** 的概念。所以"让小智AI 识别固件的主从模式"这个说法本身不成立。

正确的做法是：

> **把 obd_brz_gauge 的「从表模块」移植进小智AI 固件**，
> 让这块板变成一块"会说话的从表"。

角色不是"识别"出来的，而是**我们在代码里写死的**（一个编译期宏或 NVS 配置项）。

## 二、从表数量问题的准确答案（更正我之前的说法）

### ❌ 我之前说"4 屏超出已验证范围"——不准确

### ✅ 源码给出的准确答案

```c
#define MG_MAX_SLAVES  4   // max slaves the master tracks
```

**主表最多跟踪 4 个从表。** 所以：

| 方案 | 折算 | 代码支持？ | 官方实测？ |
|---|---|---|---|
| 1 AI + 2 仪表 | 1 主 + 2 从 | ✅ | ✅ 已实测（三连表） |
| 1 AI + 3 仪表 | 1 主 + 3 从 | ✅ **在 4 的上限内** | ❌ 未实测 |

→ **1 主 + 3 从 是代码支持的**，只是官方没实测过。

### 你对广播的理解完全正确 ✅

源码证据：

```c
static const uint8_t s_broadcast_mac[6] = {0xFF,0xFF,0xFF,0xFF,0xFF,0xFF};
esp_now_send(s_broadcast_mac, (const uint8_t *)&pkt, sizeof(pkt));
```

- 主表发的是**一个广播帧**，`FF:FF:FF:FF:FF:FF`，**发出去就完事**
- **空中时间与接收方数量无关** → 从表数量**不影响主表的发送负担** ✅
- 主表唯一的"每从表开销"是收**心跳包**：

```c
#define PRESENCE_INTERVAL_MS 500   // 从表每 500ms 发一个心跳
```

每个从表每 500ms 发一个约 6 字节的小包（`espnow_presence_t`）。
3 个从表 = 每秒 6 个小包 —— **可以忽略不计**。

**所以：从表数量对主表基本无影响，你的判断是对的。**

我上次的谨慎点其实只在"没有实测过"，不在"技术做不到"。

## 三、★ 真正的障碍：ESP-NOW 信道被写死为 1

### 源码

```c
#define ESPNOW_CHANNEL  1
// 注释原文：
// master and slaves must share a channel
// (fixed here when STA is not connected to an AP)

ESP_ERROR_CHECK(esp_wifi_set_mode(WIFI_MODE_STA));
ESP_ERROR_CHECK(esp_wifi_start());
ESP_ERROR_CHECK(esp_wifi_set_channel(ESPNOW_CHANNEL, WIFI_SECOND_CHAN_NONE));
```

### 问题所在

注释里那句 **"when STA is not connected to an AP"** 就是命门：

| 板子 | 角色 | 射频用途 |
|---|---|---|
| 仪表板（主） | MASTER | BLE 连 OBD + ESP-NOW（信道 1），**不连路由器** |
| 仪表板（从） | SLAVE | 只 ESP-NOW（信道 1），**不连路由器** |
| **小智AI 板** | SLAVE | **必须连路由器上云** + ESP-NOW |

**ESP32 的 STA 一旦连上 AP，射频信道会被强制切到 AP 的信道。**

所以：
- 路由器在信道 6 → 小智AI 板的射频在**信道 6**
- 主表在**信道 1** 广播
- **两块板互相听不见** ❌

### 解决方案（三选一）

| 方案 | 做法 | 难度 | 评价 |
|---|---|---|---|
| **① 把 AP 设成信道 1** | 手机热点/车载 WiFi/路由器改成信道 1 | 极低 | ⭐ **先这么干** |
| ② 动态对齐信道 | 小智AI 连上 AP 后读取 AP 信道，`esp_wifi_set_channel()` 对齐；主表也用该信道 | 中 | 正解，但要改两边代码 |
| ③ 主表也连同一个 AP | 主表连 AP 后信道自动对齐 | 低 | 但给主表增加 WiFi 负载（它已在跑 BLE+ESP-NOW） |

> **方案 ① 是最省事的验证路径**：先把热点设成信道 1，验证通路能否打通；
> 通了之后再做方案 ② 让它自动化。

## 四、好消息：广播包里 AI 需要的数据全都有

主表 10Hz（`BROADCAST_INTERVAL_MS 100`）广播的完整结构：

| 字段 | 含义 | 阿特兹可用？ |
|---|---|---|
| `rpm` | 转速 | ✅ |
| `speed` | 车速 | ✅ |
| `coolant_temp` | 水温 | ✅ |
| `intake_temp` | 进气温度 | ✅ |
| `oil_temp` | 机油温度 | ✅（需马自达 Mode 22 支持） |
| `load_pct` | 发动机负荷 | ✅ |
| `tps` | 节气门 | ✅ |
| `bat_mv` | 电瓶电压 | ✅ |
| `afr_x100` | 空燃比 ×100 | 多数车不支持 |
| `flags` | bit0=OBD已连, bit1=联动测试中 | ✅ |
| `seq` | 包序号（丢包诊断用） | ✅ |

**结论：AI 报警逻辑需要的水温、油温、转速、车速、电压、负荷，全都有。** ✅

## 五、移植清单（依赖链已理清）

从 `espnow_link.c` 的 `#include` 实际依赖：

```c
#include "espnow_link.h"
#include "app_obd_dsp/app_event.h"        // 事件队列
#include "app_obd_dsp/obd_data_cache.h"   // 车况缓存 ★核心
#include "bsp_obd_dsp/elm327_ble_client.h"// 只为 elm327_ble_is_connected()
#include "bsp_obd_dsp/nvs_storage.h"      // 存主表 MAC ★核心
```

### 只做从表的话，可以砍掉一半

| 模块 | 从表需要？ | 说明 |
|---|---|---|
| `wifi_espnow_init()` | ✅ | ESP-NOW 初始化 |
| `handle_rx()` → `handle_obd()` → `apply_packet()` | ✅ | **收包核心** |
| `espnow_link_start_slave()` | ✅ | 启动从表 |
| `slave_presence_task()` | ✅ | 发心跳（主表靠它统计在线） |
| `espnow_link_slave_has_data()` / `get_master_name()` | ✅ | 状态查询 |
| `espnow_link_bind_master()` | ✅ | 绑定主表 MAC（存 NVS） |
| `obd_data_cache.c/h` | ✅ | 车况缓存 |
| `nvs_storage`（取 `espnow_master_mac` 部分） | ✅ | |
| `elm327_ble_is_connected()` | ❌ | 只用于 `master_pack()`，从表不需要 → **删掉或桩掉** |
| `ui_sweep_get_step()` / `ui_intro_get_step()` | ❌ | 只用于 `master_pack()` → **删掉** |
| `master_pack()` / `master_task()` / `master_linktest_task()` | ❌ | 主表专用 → **删掉** |
| 联动测试 / 阈值同步 | ❌ | 可选，先不做 |

**移植量估算：约 400~600 行**（从表路径 + 缓存），**不涉及 LVGL、不涉及 ELM327 BLE 客户端**。
→ 比"两个完整固件合并"简单得多。

### 还要处理的两个冲突

1. **BLE 占用**：小智AI 用 BLE 做配网（BluFi，见官方 `docs/blufi.md`）；
   而绑定主表需要通过 BLE 扫描读主表 MAC。
   → 两者**时间上不重叠**（配网一次、绑定一次），可以共存，但要串行化。
2. **信道**：见第三节，必须先解决。

## 六、"做出提示"的三种机制对比（基于官方文档）

| 机制 | 方向 | 延迟 | 需联网 | 需改服务端 | 适合 |
|---|---|---|---|---|---|
| **本地预录音频** | 设备内部 | <100ms | ❌ | ❌ | ⭐ **安全告警** |
| **MCP 工具** `tools/call` | 云端 → 设备 | 1~3s | ✅ | ❌ | ⭐ **用户问答** |
| **notify 通知** | 云端 → 设备 | 1~3s | ✅ | ✅ 需自建 | 云端资讯播报 |

### 官方文档明确的事实

- **MCP**：设备用 `McpServer::AddTool(名字, 描述, 参数, 回调)` 注册工具；云端通过
  `tools/list` 发现、`tools/call` 调用。→ **注册一个 `self.car.get_status` 工具即可实现问答** ✅
- **notify**：**方向是云端 → 设备**，云端提供 `audio_url`（单声道 Ogg Opus），设备拉取播放；
  **无确认、无 ID、尽力投递、只在 Idle 状态接受、忙时忽略第二条**。
  → 用它做告警需要"设备上报 → 云端生成 TTS → 下发 notify"，**链路长且要自建服务端** ❌
- 设备主动发 MCP notification：官方文档承认 `Application::SendMcpMessage` 存在，
  但**代码示例中没有明确用例**，需看代码确认。

### 推荐架构

```
安全告警（水温过高、转速超红线）
   └→ 本地预录音频，<100ms，断网可用  ⭐

用户问答（"水温多少"）
   └→ MCP 工具 self.car.get_status，LLM 自行调用  ⭐

（可选，以后再说）资讯播报
   └→ notify，需自建服务端
```

## 七、结论

| 问题 | 答案 |
|---|---|
| 小智AI 能"识别"主从模式吗？ | ❌ 概念不存在，正确做法是**移植从表模块** |
| 从表数量影响主表吗？ | ❌ **基本不影响**（广播 O(1)，心跳可忽略），你说得对 |
| 最多支持几个从表？ | **4 个**（`MG_MAX_SLAVES`），所以 1主+3从 代码支持 |
| 最大障碍是什么？ | ⚠️ **ESP-NOW 信道写死为 1，与小智AI 连的路由器信道冲突** |
| 最省事的验证路径 | 把 AP（手机热点）设成**信道 1**，先打通通路 |
| AI 能拿到哪些数据？ | 水温/油温/转速/车速/电压/负荷/TPS 全都有 ✅ |
| 告警怎么做？ | **本地预录音频**；问答用 **MCP 工具** |
| 移植量 | 约 400~600 行，不碰 LVGL 和 ELM327 客户端 |
