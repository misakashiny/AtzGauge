### 三处必须理解的设计决定（原文写在 `espnow_link.c` 文件头）

1. **不初始化 WiFi、不设信道**。上游 `wifi_espnow_init()` 会 `set_mode/start/set_channel`，但小智的 WiFi 归 `WifiBoard` 管且必须连路由器上云。本模块只 `esp_now_init()`。信道跟随 STA（`peer.channel = 0`）。
2. **不依赖 NVS**。绑定主表 MAC 的接口已留出，但只作用于内存。
3. **启动时机**。`espnow_slave_start_async()` 起后台任务，**等 STA 真正连上 AP（信道确定）后**才 `esp_now_start()`；配网阶段是 APSTA、信道未定，那时启动会对不齐。

### 5.3 阶段 C：ESP-NOW 与 WiFi STA 的信道对齐 ✅（方案①）

**问题**（`07` 号文档第三节）：上游主表把信道**硬编码为 1**；而 ESP32 的 STA 一旦连上 AP，射频信道会被强制切到 AP 的信道。路由器在信道 6 → 从表射频在 6 → 主表在 1 → **互相听不见**。

**本次采用方案①「AP 设成信道 1」**，实测日志直接自证：

```
I (61168) espnow_slave: ESP-NOW slave up; following STA channel 1 (master broadcasts on ch1)
```

从表读取到的 STA 信道就是 **1**，与主表一致 —— 通路在信道这一层已经打通。代码还会在同信道不匹配时主动告警：

```
W (xxxx) espnow_slave: STA is on channel 6 but the gauge master broadcasts on channel 1
         -> set your router/hotspot to channel 1 or no packets will arrive
```

**为什么不做自动切信道**：STA 连上 AP 后射频信道由 AP 决定，强行 `esp_wifi_set_channel()` 会把云连接踢掉（小智必须联网上云）。所以从表侧只跟随、只告警。真正的"正解"是方案②（两边都动态对齐），需要同时改主表，见第六节。

`self.car.get_status` 在**全局 MCP 工具之前**注册成功。它把车况 + 链路新鲜度组装成文本给云端 LLM，工具描述里明确写了"没有数据时不要编造读数"。

## 八、本次会话新增的信道诊断（值得一提的设计）

**问题**：ESP-NOW 默认 `peer.channel = 0` = 跟随 STA 信道，而主表固定在信道 1。若 STA 连到别的信道的路由器，从表**一个包都收不到**——这和「主表没开机 / 距离太远」在本模块里**曾经完全无法区分**，排查只能靠猜。

**做法**：ESP-NOW 信道不对时，射频偶尔仍会漏进来几个本不属于我们的帧。于是把「长度/魔数不匹配」的帧计数并记录最后来源 MAC，就能给出方向性判据：

| 现象 | 判断 |
|---|---|
| mismatch 持续增长，却没有有效包 | 射频是活的，但收到的是别人的流量 → **大概率信道不对** |
| mismatch 恒为 0 | 这个信道上根本没有 ESP-NOW 流量 → **主表没开或太远** |

实现：`espnow_link.c` 的 `chan_monitor_task` 每 5s 检查一次，条件满足就主动打 `ESP_LOGW`；同一判据也接进了 MCP 工具，所以**语音问"水温多少"时，模型能直接说出"链路没数据但收到了外来帧，多半是信道不对"**，而不是笼统地说"没有数据"。

### ★ 如果将来还要碰触摸，这五个坑是真实存在的（别再踩一遍）

**坑 1：不能用 `lv_indev_active()` 在定时器里"找"输入设备。**
它直接返回全局 `indev_active`，而该字段只在 `lv_indev_read()` 执行期间被赋值、返回前清空。
普通 `lv_timer` 回调里通常是 NULL（偶发残留非 NULL）→ "按下"几乎永远检测不到。
必须由板级把真实句柄传进来。

**坑 2：定时器不能在自己静止时 pause 掉。**
一旦暂停就没人再轮询触摸，新的按下永远发现不了 —— 唤醒源不存在。要常驻定时器 + 空闲时极短提前返回。

**坑 3：绑定/改样式必须幂等，否则触发看门狗。**
小智在**每一次状态变化**时都会调 `SetEmotion()`（`application.cc:1011`）。
若在那里做写样式/重绘，状态机每变一次就打一次重绘，主任务会被刷到
`task_wdt`（IDLE0 饿死，backtrace 停在 `lv_inv_area`）。
另注：`lv_obj_get_width()` 返回的是**应用 transform 之后**的尺寸，
所以必须先归位缩放再量尺寸，否则每切一次表情放大一倍。

**坑 4：配网模式下表情包根本没挂载。**
小智只在 `ActivationTask()` 里调 `CheckAssetsVersion() → assets.Apply()`
（`application.cc:364-369`），而它需要联网激活。
**所以未联网时 `SetEmotion()` 查不到图、退回字体图标** ——
看到的是那个单调的机器人图标，而不是表情包里的图。
（本轮按要求把这个"提前挂载"的修复也一并撤了，即恢复原版行为。
若哪天觉得"没联网就看不到表情"很别扭，这条就是原因和解法。）

**坑 5：`esp_lvgl_port` 的触摸读失败即 abort。**
`esp_lvgl_port_touch.c:127` 是 `ESP_ERROR_CHECK(esp_lcd_touch_read_data(...))`，
而 CST816S 有相当比例的读会失败（NACK → `ESP_ERR_INVALID_RESPONSE`，
且 NACK 只在 DEBUG 级别打日志、默认看不见）→ **无限重启**（实测 54 次 abort）。
另外只要 `int_gpio_num != NC`，它还会把输入设备切成 `LV_INDEV_MODE_EVENT`（只靠中断）。
若要自己接，就绕开 lvgl_port：直接 `esp_lcd_panel_io_rx_param(tp_io_, 0x02, d, 5)`
轮询，失败当作"未按下"重试。

| 项 | 值 |
|---|---|
| 控制器 | CST816S，I2C 地址 0x15，IC id 读到 181 / ChipID 0xB5 / 固件 0x04 |
| 总线 | **独立** I2C_NUM_1：SDA=GPIO1，SCL=GPIO3 |
| 复位 | `TP_PIN_NUM_RST = NC`，实际由 TCA9554 的 EXIO0/EXIO1 一起复位 |
| I2C 面板 IO | **不能用**组件的 `ESP_LCD_TOUCH_IO_I2C_CST816S_CONFIG()` 宏：它按旧字段顺序写，而 IDF 6.1 把 `on_color_trans_done`/`user_ctx` 提到了 `flags` 之前，C++ 指定初始化要求顺序一致 → 编译报错。要本地按 6.1 顺序写一份 |

## 十、触摸屏幕开始对话（本轮新增 · 2026-09-14 晚）

> **一句话**：点一下屏幕 = 开口说话。**只在「空闲」状态生效**，其余状态一律忽略，
> 所以 AI 正在回答时误触不会把它打断 —— 这是明确的产品选择，不是漏做。

### 设计（怎么绕开第九节那 5 个坑）

| 决定 | 原因 |
|---|---|
| **不接 LVGL**，用独立任务轮询 | 一次绕开坑 1/2/3：不需要 `lv_indev_active()`、不需要"常驻定时器"那套、不碰任何样式绑定；也不需要 LVGL 锁 |
| **不用 `esp_lcd_panel_io`**，直接用 `i2c_master_transmit_receive` | 见下面**坑 6**：panel-IO 层把每次 NACK 都打成 ERROR |
| 读失败 = **"未按下"**，绝不 `ESP_ERROR_CHECK` | 直接避开坑 5（那正是上一轮无限重启的根因） |
| 触发走 `Application::ToggleChatState()` | 它只置事件位、由主循环处理，跨任务安全（符合 `AGENTS.md` 对回调的约束） |

代码：`main/boards/waveshare/esp32-s3-touch-lcd-1.85-atzgauge/esp32-s3-touch-lcd-1.85-atzgauge.cc`
（`InitializeTouchWake()` / `TouchTryBus()` / `TouchPollTask()`）。可调参数：

| 宏 | 默认 | 说明 |
|---|---|---|
| `TP_POLL_INTERVAL_MS` | 30 | 轮询周期（ms） |
| `TP_CONFIRM_SAMPLES` | 2 | 连续两次读到手指才算"按下"（≈60ms 去抖） |
| `TP_PROBE_ATTEMPTS` / `TP_PROBE_GAP_MS` | 10 / 100 | 启动探测重试次数 / 间隔 |
| `TP_DIAG` | 0 | 置 1 → 每 5s 打一行 `touch diag: ok=… fail=…`，用来判断"面板到底答不答" |

### ★ 本轮新踩的三个坑（已同步进 18 号缺陷台账）

**坑 6 · `esp_lcd_panel_io` 把正常 NACK 打成了 ERROR。**
CST816S 空闲时会休眠、**不应答自己的 I2C 地址**，这是它的正常行为；但
`panel_io_i2c_rx_buffer()` 对每次失败都 `ESP_LOGE` —— 30ms 轮询下实测
**45 秒刷了 1094 行 ERROR**（日志 102 KB，其中绝大部分是它）。
IDF 原生 `i2c_master.c` 对 NACK 只打 `ESP_LOGD`（`s_i2c_err_log_print()` 里还有
`bypass_nack_log` 开关），换成原生 API 后同样行为**零日志**。
两条路径底层是同一个 `i2c_master_transmit_receive()` 调用，功能完全等价 —— 换的是日志噪音，不是能力。

**坑 7 · `i2c_master_probe()` 在这块板上不可靠。**
用它扫描总线时，**连已知工作正常的 TCA9554（bus0 @0x20）都扫不出来**。
所以"扫描不到设备"**不能**作为设备不存在的证据。要探测就得用**真实寄存器读**
（本项目用 CHIP_ID `0xA7`）。

**坑 8 · 单次探测会误判。**
TCA9554 复位脉冲放开后约 100ms 就去读，芯片还在启动 → NACK → 误报"面板没接"。
必须重试（10 次 × 100ms）。

### 验证证据（第一版固件，2026-09-14 21:54 实测通过）

```
I (1168) waveshare_lcd_1_85: CST816S answered (finger_num=0)      ← 面板应答
I (6678) waveshare_lcd_1_85: touch tap -> start conversation      ← 点屏被识别
I (6678) StateMachine: State: idle -> connecting                  ← 对话链路被拉起
I (6748) StateMachine: State: connecting -> listening
```

第二次点屏（14.1s）同样 `idle -> connecting -> listening`。**功能链路本身已验证成立。**

### ★ 结论更正（2026-09-15 晚）：不是硬件问题，是**读取路径的回归** —— 已修复

**之前那份"硬件待查"的判断是错的。** 用户提醒"以前有版本能用"，我照做了一次 A/B：把
**09-14 21:54 那版实测可用的实现原样恢复**（`TP_LEGACY_PATH=1`），结果立刻恢复：

```
I (1168) touch(legacy): CST816S answered (finger_num=0)   ← 探测成功
I (10678) touch tap -> start conversation                 ← 检测到真实点击
```

面板一直是好的。**是我在 22:00 左右为了消除 NACK 日志刷屏，把读取路径从
`esp_lcd_panel_io` 换成了原生 `i2c_master`（并把超时从"无限等待"改成 50ms），
顺带把 GPIO4 配成上拉输入 —— 从那以后就再没读到过触摸。**

| 项 | ✅ 可用版（21:54） | ❌ 失效版（22:00 之后） |
|---|---|---|
| 读取 | `esp_lcd_panel_io_rx_param()` | `i2c_master_transmit_receive()` |
| 超时 | **无限等待**（panel-IO 默认 `-1`） | **50 ms** |
| GPIO4 / TP_INT | **完全不碰** | 配成输入 + 上拉 |
| 探测失败后 | **继续轮询**（随后读到了真实触摸） | 拆总线 + 禁用功能，后续靠后台重试 |

最可能的原因是**超时**：CST816S 从休眠唤醒时会拉长时钟（clock stretching），
50ms 一超时就中止事务；而无限等待会等它把数据给完。

**修法（两个都要）**：

1. 读取路径改回能用的 `esp_lcd_panel_io`（`TP_LEGACY_PATH=1`），GPIO4 不碰；
2. 日志刷屏改为**只关掉那个 tag**：`esp_log_level_set("lcd_panel.io.i2c", ESP_LOG_NONE)`。
   实测 20 秒的日志从 347 行 ERROR 降到 **0 行**，日志体积 41271 → 12575 字节。
   真实故障仍可从 `/touch` 自检端点和 `TP_DIAG` 计数看出来，**不是把问题藏起来**。

> **教训**：为了让日志好看而改数据通路，是会改坏功能的。当时应该只压日志等级，
> 不该动读取路径 —— 而且动完之后没有用"点屏幕"这个唯一有效的手段复验。

### 面板的休眠特性（解释"不碰时读不到"）

| 状态 | 行为 |
|---|---|
| 刚被 TCA9554 复位后 | **会应答**（开机探测稳定成功：`finger_num=0`） |
| 空闲几秒后 | **休眠，不应答自己的地址**（NACK）→ `/touch` 静置自检会显示 `reads_ok=0` |
| 手指按下时 | **醒来并应答** → 轮询任务连续两次读到 `finger_num>0` 就触发对话 |

所以"静置时读不到"是正常现象，**判断面板好坏必须边点边测**（这正是 `/touch` 端点的用法）。

### 现在的自愈结构（保留）

1. 启动时探测；能应答就直接开轮询任务；
2. 探测失败则每 5 秒静默重试，面板任何时候恢复都能自动接上，无需重刷固件。

### ★ 30 秒一键自检

设备联网后，用浏览器打开（手机也行）：

```
http://<设备IP>:8099/touch?seconds=15
```

打开后**点屏幕**，页面会直接给出结论：

| 页面显示 | 含义 |
|---|---|
| `TOUCH DETECTED` | 面板工作正常 → 若仍不触发对话，才是固件逻辑问题 |
| `chip answering, but no touch seen` | 芯片在、但没读到手指（面板贴合/灵敏度问题） |
| `panel NOT RESPONDING on I2C` | **面板完全不应答 → 硬件侧问题，固件无能为力** |

这一个 URL 就把"固件问题"和"硬件问题"彻底分开了，不用再来回刷固件试。

下一步（按可能性排序）：

1. **检查触摸 FPC 排线**（屏幕模组背面那条较窄的软排线）是否插到位 —— 目前最可能的原因
   （※ 用户反馈：该排线在模组背面**看不到/够不着**，所以这条暂时做不了）
2. 确认是**真断电**：拔掉 USB 等 10 秒再插（按复位键不算）
3. 若仍无应答，可用出厂整片备份 `backup/factory-16MB.bin` 做出厂 UI 的触摸判定
   （⚠️ 整片写入会覆盖 NVS，含 WiFi 凭据与激活状态，需要重新激活）
   —— 出厂固件在 09-13 到货时**触摸是确认可用的**，所以这是最硬的对照
4. **不必卡在这里**：机身 BOOT 键单击 = 开始/结束对话（原版行为），功能上不缺什么
